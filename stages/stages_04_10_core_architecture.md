### 第1层：任务归一建模层

**唯一职责**：将任意形式的任务输入，归一化为标准的 Task Quartet 结构

**解决痛点**：
- 目标模糊 → 强制明确化
- 目标跑偏 → 固定目标锚点
- 无终止条件 → 可验证的终止规则

**边界范围**：
- ✅ 任务目标提取和归一化
- ✅ 前置条件识别和建模
- ✅ 边界约束识别和建模
- ✅ 终止规则定义和验证
- ❌ 任务拆解（下一层职责）
- ❌ 依赖管理（下一层职责）
- ❌ 执行控制（下一层职责）

---

### 第2层：拓扑依赖拆解层

**唯一职责**：将主任务拆解为子任务，建立依赖关系，形成合法 DAG

**解决痛点**：
- 任务遗漏 → 完整性检查
- 执行乱序 → 拓扑排序
- 循环依赖 → DAG 验证

**边界范围**：
- ✅ 子任务拆分策略
- ✅ 依赖关系识别
- ✅ DAG 构建
- ✅ DAG 合法性验证
- ✅ 拓扑排序
- ❌ 原子动作（下一层职责）
- ❌ 具体执行（下一层职责）

---

### 第3层：原子动作收敛层

**唯一职责**：将子任务进一步拆解为原子动作，形成执行队列

**解决痛点**：
- 粒度太粗 → 强制原子化
- 粒度不均 → 统一粒度标准
- 不可控执行 → 原子动作队列

**边界范围**：
- ✅ 原子动作判定
- ✅ 动作队列生成
- ✅ 粒度控制
- ✅ 原子动作执行
- ❌ 全局验证（上一层职责）
- ❌ 任务调度（上一层职责）

---

### 第4层：分段校验收敛层

**唯一职责**：在各个关键节点进行验证，确保整体收敛，异常处理

**解决痛点**：
- 无法终止 → 终止条件验证
- 错误扩散 → 早发现早处理
- 无熔断机制 → 熔断和回滚

**边界范围**：
- ✅ 前置条件验证
- ✅ 执行结果验证
- ✅ 约束全程检查
- ✅ 终止条件验证
- ✅ 熔断机制
- ✅ 回滚机制
- ❌ 具体拆解（下一层职责）

## 📝 第5阶段：Task Quartet 规范文档

### 四元组字段定义

| 字段 | 英文 | 类型 | 必需 | 说明 |
|------|------|------|------|------|
| 目标 | Target | String | ✅ | 唯一、明确、可验证 |
| 前置条件 | Preconditions | List[Condition] | ❌ | 任务开始前必须满足 |
| 约束 | Constraints | List[Constraint] | ❌ | 全程必须遵守 |
| 终止规则 | EndRule | Function | ✅ | 判定任务完成 |

---

### 1. Target（目标）字段规则

**判定标准**：
1. ✅ 唯一性：只有一个核心目标
2. ✅ 明确性：描述具体，不模糊
3. ✅ 可验证：有明确的完成判定

**反例**：
- ❌ "做个网站"（太模糊）
- ❌ "优化代码"（没有标准）
- ❌ "又快又好"（多目标冲突）

**正例**：
- ✅ "生成一个Python脚本，读取data.csv，计算平均值，输出到result.txt"
- ✅ "在当前目录创建一个index.html，包含标题、导航、内容三个区域"

---

### 2. Preconditions（前置条件）字段规则

**判定标准**：
1. ✅ 可验证：可以明确判断是否满足
2. ✅ 必要性：确实是任务开始前必需的
3. ✅ 不冗余：不包含任务执行中会处理的

**示例**：
```python
Preconditions: [
  "data.csv文件存在",
  "Python环境可用",
  "当前目录可写"
]
```

---

### 3. Constraints（约束）字段规则

**判定标准**：
1. ✅ 可检查：可以在执行中验证
2. ✅ 明确边界：清晰的限制条件
3. ✅ 可量化：有具体数值更佳

**约束类型**：
- 步骤数限制：最多10步
- 时间限制：最多5分钟
- 资源限制：不读取外部网络
- 范围限制：不修改系统文件

---

### 4. EndRule（终止规则）字段规则

**判定标准**：
1. ✅ 可判定：函数返回 bool
2. ✅ 明确条件：不是模糊描述
3. ✅ 可达成：不是不可能的条件

**示例**：
```python
# 好的终止规则
def end_rule(context):
    return "result.txt" in os.listdir()

# 或者
def end_rule(context):
    return context.get("status") == "completed"
```

## 🔍 第6阶段：主流 Agent 规划机制对比

### 对比维度

| 维度 | 经验主义方案 | 第一性原理方案 |
|------|------------|--------------|
| 设计方法 | 补丁式，试错 | 公理式，从底层推导 |
| 目标管理 | 模糊，无锚点 | Task Quartet，固定锚点 |
| 依赖管理 | 隐式，混乱 | 显式DAG，严格验证 |
| 执行粒度 | 粗糙，凭感觉 | 原子动作，三条标准 |
| 验证机制 | 事后，薄弱 | 全程，分段验证 |
| 收敛保证 | 无保证 | 全程收敛检查 |
| 问题解决 | 补丁，复发 | 根治，不复发 |

---

### 主流方案分析

#### LangChain
- 特点：链式调用
- 问题：无明确DAG，无收敛机制
- 对比：我们有完整的DAG和收敛

#### AutoGPT
- 特点：自主Agent
- 问题：目标容易跑偏，无限循环
- 对比：我们有固定目标锚点

#### BabyAGI
- 特点：任务队列
- 问题：无明确终止条件，粒度不可控
- 对比：我们有Task Quartet终止规则

## 🌐 第7阶段：DAG 拓扑依赖原理

### DAG 定义
- Directed（有向）：边有方向
- Acyclic（无环）：没有循环
- Graph（图）：节点和边

---

### DAG 约束规则

| 规则 | 说明 | 违反后果 |
|------|------|---------|
| 无循环 | A不能依赖B且B依赖A | 死锁 |
| 无悬空 | 所有节点都从入口可达 | 孤立节点 |
| 唯一入口 | 只有一个开始节点 | 混乱 |
| 明确依赖 | 所有依赖关系显式声明 | 遗漏 |

---

### DAG 禁例

❌ 禁例1：循环依赖
```
A → B → C → A
```

❌ 禁例2：悬空节点
```
A → B     C (孤立)
```

❌ 禁例3：多个入口
```
A        B
 ↓        ↓
 C        D
```

✅ 正例
```
   A
  / \
 B   C
  \ /
   D
```

## ⚛️ 第8阶段：原子动作三条判定公理标准

### 原子动作定义
原子动作是最小执行单元，满足以下三条标准。

---

### 公理1：单一职责原则
**表述**：一个原子动作只做一件事，只有一个成功或失败结果

**判定规则**：
- ✅ 只有一个主要目标
- ✅ 输出清晰单一
- ✅ 职责没有交叉

**反例**：
- ❌ "读取文件并分析并保存"（三件事）

**正例**：
- ✅ "读取data.csv文件内容"

---

### 公理2：不可再分原则
**表述**：原子动作不能有意义地拆分为更小的动作

**判定规则**：
- ✅ 拆分后失去意义
- ✅ 拆分后无法独立执行
- ✅ 是基本操作单元

**反例**：
- ❌ "写一个脚本"（可再分）

**正例**：
- ✅ "打开文件"
- ✅ "写入一行内容"
- ✅ "关闭文件"

---

### 公理3：可直接执行原则
**表述**：原子动作不需要进一步规划，可以直接执行

**判定规则**：
- ✅ 执行指令明确
- ✅ 不需要进一步决策
- ✅ 有明确的输入输出

**反例**：
- ❌ "想办法解决问题"（需规划）

**正例**：
- ✅ "执行命令: ls -la"
- ✅ "调用API: POST /data"

## 🛡️ 第9阶段：收敛机制规范

### 收敛机制架构

```
任务执行
    ↓
[预校验] → ✗ → 熔断/回滚
    ↓ ✓
[执行]
    ↓
[执行校验] → ✗ → 熔断/回滚
    ↓ ✓
[约束检查] → ✗ → 熔断/回滚
    ↓ ✓
[终止检查] → ✓ → 完成
              ✗ → 继续
```

---

### 1. 预校验规则

**触发时机**：任务/动作执行前

**检查内容**：
- 前置条件满足？
- 依赖关系完整？
- 约束当前满足？
- 输入合法？

**失败处理**：
- 立即停止
- 记录原因
- 触发回滚或等待

---

### 2. 执行校验规则

**触发时机**：任务/动作执行后

**检查内容**：
- 输出符合预期？
- 结果有效？
- 没有异常状态？

**失败处理**：
- 标记失败
- 触发重试
- 或熔断回滚

---

### 3. 熔断规则

**触发条件**：
- 连续失败 N 次
- 约束严重违反
- 检测到死循环
- 递归超过深度

**熔断动作**：
- 立即停止执行
- 保存当前状态
- 记录完整日志
- 通知异常

---

### 4. 回滚规则

**回滚策略**：
- 记录执行历史
- 按相反顺序回滚
- 恢复到上一个稳定点
- 可选：尝试其他路径
